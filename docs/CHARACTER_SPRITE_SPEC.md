## 1. 만들어야 하는 파일 목록

캐릭터 3종은 백엔드 `ALLOWED_CHARACTER_IDS`와 1:1 대응합니다
(`backend/.../member/service/MemberService.java:46`).

| 백엔드 ID | 파일 접두어 |
|---|---|
| `PALBANG` | `palbang` |
| `PALBANG_RABBIT` | `palbang_rabbit` |
| `PALBANG_DOG` | `palbang_dog` |

### 네이밍 규칙

```
frontend/assets/sprites/{접두어}_{상태}_{방향}.webp
```

전부 소문자, 구분자는 `_`. 예: `palbang_walk_ne.webp`, `palbang_dog_idle_s.webp`

### 방향 — 최대 5개만 만듭니다 (v1은 이 중 2개)

좌우 대칭을 이용해 3방향은 코드에서 `scaleX: -1`로 처리합니다 (§7.1, 37% 절감).
아래 5방향이 제작 가능한 전체 목록이고, **v1에서 실제로 그릴 것은 `n`과 `s` 둘뿐**입니다
(이유는 바로 다음 절).

| 만들 것 | 방위 | 화면에서 보이는 모습 |
|---|---|---|
| `n` | 북 | 뒤통수 |
| `ne` | 북동 | 등 + 오른쪽 반측면 |
| `e` | 동 | 오른쪽 완전 측면 |
| `se` | 남동 | 앞 + 오른쪽 반측면 |
| `s` | 남 | 정면 |

| 만들지 않을 것 | 코드에서 이렇게 만듭니다 |
|---|---|
| `nw` | `ne` + `scaleX: -1` |
| `w` | `e` + `scaleX: -1` |
| `sw` | `se` + `scaleX: -1` |

> ⚠️ **비대칭 요소를 넣지 마십시오.** 한쪽 어깨 가방, 한 손에만 든 물건, 한쪽 가슴 로고, 가르마 방향 —
> 반전하면 반대쪽으로 옮겨가서 눈에 띕니다. 좌우 대칭 디자인이거나, 비대칭 요소가 있다면
> 8방향 전부 제작해야 합니다 (파일 수 5 → 8로 증가).

### 최종 파일 수 — v1은 9개로 시작합니다

현장 지도는 `followUserMode={FollowWithHeading}` 입니다 (`field/[sessionId].tsx`).
이 모드는 **기기 나침반 방향이 화면 위쪽이 되도록 지도를 회전**시킵니다.
사용자는 보통 자기가 바라보는 쪽으로 걸으므로, 화면 기준 상대 방향은 거의 항상 `n`(뒤통수)입니다.
**5방향을 다 그려도 4개는 거의 안 쓰입니다.** 그래서 최소 구성으로 시작합니다.

| 단계 | 파일 수 | 구성 |
|---|---|---|
| **v1 (권장)** | **9개** | 캐릭터당 `walk_n` · `walk_s` · `idle_s` |
| 방향 확장 | +9개 | `walk_ne` · `walk_e` · `walk_se` 추가 (총 18개) |

v1의 세 장이 각각 담당하는 상황:

| 파일 | 언제 보이는가 |
|---|---|
| `walk_n` | 걷는 중. heading 추적이 켜져 있으면 사실상 이것만 보입니다 |
| `walk_s` | 사용자가 지도를 손으로 180° 돌린 채 걸을 때 |
| `idle_s` | 정지 중, 그리고 위치 사용 불가 시 정적 대체 |

**방향을 나중에 늘려도 중간 상태가 어색하지 않습니다.** 등록 안 된 방향은
각도상 가장 가까운 등록된 방향으로 대체됩니다 (`spriteConfig.ts` 의 `findNearestSheet`).
`walk_n` 만 있으면 `nw`/`ne` 요청이 전부 `n` 으로 흡수됩니다.

> **왜 "정면 고정" 대체가 아니라 "가장 가까운 방향" 대체인가**
>
> 아파트 단지는 철근 구조물 때문에 지자기 간섭이 커서 기기 나침반이 ±15~30° 씩 흔들립니다.
> `FollowWithHeading` 은 그 값으로 지도를 회전시키므로 상대 방향이 `n` 에 고정되지 않고
> `nw`/`n`/`ne` 사이를 오갑니다. 이때 정면으로 떨어뜨리면 **걷는 중에 캐릭터가 갑자기
> 카메라를 쳐다봅니다.** 각도 기준 대체라야 이 깜빡임이 없습니다.

#### 5방향 전부를 쓰고 싶다면

카메라를 `Follow`(정북 고정)로 바꾸면 5방향이 모두 쓰입니다. 지도 라벨이 회전하지 않아
한글 아파트명이 읽기 쉬워지는 이점도 있습니다. 코드 변경은 `followUserMode` 한 줄이고,
방향 판정 로직은 지도 heading 을 빼는 방식이라 **두 모드 모두에서 이미 올바르게 동작합니다.**
다만 이건 아트 개수 문제가 아니라 **UX 선택**이므로, 회전 지도가 임장에 더 맞다고 판단되면
v1 9개 구성을 유지하는 것이 맞습니다.

## 2. 프레임 수와 재생 속도

§7.1의 "37프레임"은 확정값이 아니라 가정이었고, 문서 자체가 *"37프레임 ÷ 10fps = 3.7초/사이클이면
슬로우모션"* 이라고 지적하고 있습니다. 아래로 확정합니다.

| 상태 | 프레임 수 | 사이클 길이 | 재생 fps | 내용 |
|---|---|---|---|---|
| `walk` | **12** | 1.0초 | **12fps** | 양발 1보씩 = 1사이클. 첫 프레임과 마지막 프레임이 이어져야 함(루프) |
| `idle` | **8** | 2.0초 | **4fps** | 호흡·가벼운 무게 이동 정도. 과한 동작 금지 |

**왜 12프레임인가** — 보행 케이던스는 한 걸음 약 0.5초입니다. 양발 1사이클 = 1.0초.
12프레임/1.0초 = 12fps는 캐릭터 애니메이션에서 충분히 부드러운 하한이고,
37프레임 대비 디코딩 메모리가 1/3입니다. 동시 표시가 1개라 프레임을 더 쓸 이유가 없습니다.

**정적 대체 상태(위치 사용 불가)** 는 별도 에셋을 만들지 않습니다.
`idle_s`의 0번 프레임을 그대로 정지 표시합니다.

## 3. 시트 레이아웃

**가로 1행 스트립**으로 만듭니다. 행 넘김이 없어야 Reanimated에서 `translateX` 하나로 프레임을 넘길 수 있습니다.

| 상태 | 배치 | 시트 전체 크기 |
|---|---|---|
| `walk` | 12열 × 1행 | 1536 × 128 px |
| `idle` | 8열 × 1행 | 1024 × 128 px |

- 프레임 순서는 **왼쪽 → 오른쪽**, 0번이 맨 왼쪽
- **프레임 크기: 128 × 128 px** (§7.1 권장값. 화면 표시 크기가 3x 밀도에서 논리 40~64dp이므로 충분)
- 1536px은 구형 GPU의 최소 보장 텍스처 크기(2048px) 안에 들어갑니다.
  **192px로 올리면 12×192 = 2304px로 이걸 넘겨서** 2행으로 쪼개야 하고 좌표 계산이 복잡해집니다.
  128px을 유지하십시오.

### 프레임 내부 정렬 — 여기가 제일 실수하기 쉽습니다

- **발바닥을 프레임 하단에 맞춥니다.** 지도 위에서 `iconAnchor: 'bottom'`으로 배치되므로,
  발 위치가 프레임 하단 기준선이 됩니다.
- **걷기 중 상하 바운스를 굽지 마십시오.** 3D에서 루트 본이 위아래로 흔들리면 프레임마다 발 높이가
  달라지고, 지도 위에서 캐릭터가 붕 떴다 가라앉는 것처럼 보입니다. 루트를 고정하고 굽습니다.
- **좌우는 프레임 중앙 정렬.** 걷기 중 팔이 앞뒤로 흔들려 실루엣 폭이 변하더라도 몸통 중심축은 고정합니다.
- **프레임 경계에 최소 4px 투명 여백.** 여백이 없으면 이웃 프레임 픽셀이 bilinear 필터링으로
  번져 들어옵니다(텍스처 블리딩).

## 4. 3D에서 굽는 설정

3D 모델을 런타임에 돌리는 게 아니라, **3D 렌더 결과를 미리 2D 시트로 굽는** 방식입니다 (§7.1).

| 항목 | 값 | 이유 |
|---|---|---|
| 카메라 투영 | **정사영(Orthographic)** | 원근을 쓰면 방향마다 왜곡이 달라져 8방향이 서로 안 맞습니다 |
| 카메라 고도각 | **수평에서 45° 위** | 현장 지도가 `pitch={45}`로 기울어 있습니다 (`field/[sessionId].tsx:106`). 이 각도가 안 맞으면 캐릭터 원근만 지도와 따로 놉니다 |
| 방향 회전 | 캐릭터를 Y축 기준 45° 간격 회전 (0°/45°/90°/135°/180°) | `s`→`se`→`e`→`ne`→`n` 순 |
| 배경 | **완전 투명 (알파)** | |
| 그림자 | **굽지 마십시오** | 지도 배경색이 위치마다 다릅니다. 그림자가 필요하면 코드에서 별도 타원 레이어로 깔겠습니다 |
| 조명 | 방향별로 **동일하게 고정** | 카메라만 돌리고 조명을 같이 돌리면 방향 전환 시 밝기가 튑니다 |
| 안티에일리어싱 | 켜기 | 128px은 작아서 계단이 그대로 보입니다 |

## 5. 포맷

- **WebP 무손실** (`-lossless`). PNG보다 25~35% 작고 Android 네이티브 지원입니다 (§7.1)
- **애니메이션 WebP를 쓰지 마십시오.** 정적 WebP 1장에 프레임을 가로로 늘어놓은 스프라이트 시트여야 합니다.
  애니메이션 WebP는 프레임 인덱스를 우리가 제어할 수 없습니다
- 알파 채널 유지

PNG로 먼저 출력한 뒤 변환:

```bash
cwebp -lossless -exact palbang_walk_s.png -o palbang_walk_s.webp
```

`-exact`는 투명 픽셀의 RGB값을 보존합니다. 없으면 반투명 외곽선에 색 번짐이 생깁니다.

## 6. 프론트엔드 구현 (완료)

에셋 없이 먼저 구현해 뒀습니다. 시트가 들어오면 `spriteConfig.ts`의 `SPRITE_SHEETS` 표만 채우면 됩니다.

| 구현 | 파일 |
|---|---|
| 프레임 인덱스 (`floor(elapsedMs / (1000/fps)) % frameCount`, UI 스레드) | `src/features/character/useSpriteFrame.ts` |
| 렌더러 (클리핑 View + `translateX`, 좌우 반전) | `src/features/character/CharacterSprite.tsx` |
| 시트·프레임 스펙 및 에셋 매핑 표 | `src/features/character/spriteConfig.ts` |
| 방향 판정 (이동 방위각 − 지도 heading) | `src/features/character/direction.ts` |
| 이동/정지 판정, 정지 타임아웃 | `src/features/character/useCharacterMotion.ts` |
| 좌표 → 화면 위치 변환, 오버레이 배치 | `app/(app)/field/[sessionId].tsx` |
| 선택 캐릭터 조회 | `src/features/member/api/useMyProfile.ts`, `src/features/character/useSelectedCharacter.ts` |
| 거리·방위각 계산 | `src/lib/geo.ts` |

지킨 제약:

- 프레임 인덱스는 Reanimated shared value. **zustand에 넣지 않음** (`characterStore.ts:4` 경고)
- 지도와 **형제 레이어의 절대 위치 View**. `MarkerView` 금지 ([rnmapbox#4206](https://github.com/rnmapbox/maps/issues/4206))
- `onCameraChanged`를 100ms로 스로틀 ([rnmapbox#4192](https://github.com/rnmapbox/maps/issues/4192) 대응)
- "어떻게 그릴지"는 `CharacterSprite.tsx` 한 겹에만. B안(Skia) 전환 시 이 파일만 교체

시트가 등록되지 않은 조합은 **같은 모션의 정면(`s`) 시트 → 1프레임 플레이스홀더** 순으로 자동 대체되므로,
방향을 하나씩 추가해도 중간 상태에서 앱이 깨지지 않습니다.

### 아직 남은 것

- **실기기 검증 (스파이크 2)** — Android에서 `overflow: hidden` + `transform`이 함께 걸릴 때의
  클리핑 누락 엣지케이스는 §7.1이 A안 고유 리스크로 지목한 항목입니다. S23에서 눈으로 봐야 합니다
- 챗봇 진입용 플로팅 액션 (FE-014 나머지 범위)
- `sessionId` → `apartmentId`·목적지 좌표 조회 (현재 `MOCK_FIELD_DESTINATION` 하드코딩, BE-014 대기)

## 7. 백엔드 연동

**추가 작업 없습니다.** 캐릭터 선택은 이미 구현돼 있습니다.

| 항목 | 위치 |
|---|---|
| 컬럼 | `selected_character_id VARCHAR(20) NOT NULL DEFAULT 'PALBANG'` (`V1__init_schema.sql:40`) |
| 허용값 | `PALBANG`, `PALBANG_RABBIT`, `PALBANG_DOG` (`MemberService.java:46`) |
| 조회 | `GET /api/v1/members/me` → `selectedCharacterId` |
| 온보딩 확정 | `PUT /api/v1/members/me/onboarding` |
| 마이페이지 변경 | `PATCH /api/v1/members/me` |

동시 표시가 1개로 확정됐으므로 **위치 브로드캐스트(WebSocket)도 필요 없습니다.**
스터디원 다중 표시로 범위가 넓어지면 그때 신규 백엔드 작업이 발생합니다.
