## 치명 1 — RN 0.84.1 + Expo 조합은 존재하지 않습니다

문서의 두 핵심 결정이 서로를 배제합니다.

- §7: **React Native 0.84.1 확정**
- §8: **Expo로 프로젝트 생성 확정**

Expo는 RN 버전을 직접 고르는 도구가 아니라 **SDK가 RN 버전을 결정**합니다. 그리고,

| Expo SDK | 번들 RN |
|---|---|
| SDK 55 | 0.83 |
| **SDK 56** (2026-05-21) | **0.85** |

**RN 0.84를 싣는 안정 Expo SDK는 없습니다.** 0.84는 `expo@canary`에만 존재했고, SDK 55 → 56에서 0.83 → 0.85로 건너뛰었습니다.

문서는 **Expo SDK 버전을 단 한 번도 결정하지 않습니다.** "Expo SDK"라는 단어가 전체 909줄에서 1회 등장하는데, 그마저 §4의 "구 아키텍처가 필요하면 Expo SDK 54 이하" 문맥입니다. RN 버전을 자유 변수로 놓고 §7에서 정밀하게 고른 다음, §8에서 그 자유도를 없애는 도구를 골랐는데 둘을 대조하지 않았습니다.

문서 스스로 §8.2(3)에서 **"`npx expo install`이 SDK에 맞는 호환 버전을 자동 선택"** 이라고 쓰고 있습니다. SDK가 상위 결정이라는 걸 알면서 SDK를 정하지 않았습니다.

**따라서 §7 전체가 무의미합니다.** "0.85는 미검증이니 0.84로 하향한다"는 결론이었는데, Expo를 고른 순간 0.85(SDK 56)가 강제됩니다.

**필요한 조치**

1. §7을 "RN 버전 결정"에서 **"Expo SDK 버전 결정"** 으로 재작성
2. 실질 선택지는 셋뿐: **SDK 56(RN 0.85)** / SDK 55(RN 0.83) / Bare + RN 0.84.1
3. canary는 2~3주 일정에서 선택지가 아님

**권고: SDK 56(RN 0.85).** §7이 우려한 "0.85 미검증"은 아래 치명 3·높음 4에서 보듯 근거가 약합니다.

## 치명 2 — §11 전체가 폐기된 요구사항 위에 세워졌습니다

§11은 Mapbox Secret Token(`sk.`, `DOWNLOADS:READ`) 운영에 챕터 하나를 통째로 씁니다. 그리고 이렇게 단언합니다.

> Secret Token은 `DOWNLOADS:READ` 스코프가 필요하며, **없으면 빌드 자체가 실패합니다.**

**사실이 아닙니다.**

rnmapbox PR [#4124](https://github.com/rnmapbox/maps/pull/4124) (2025-12-21 머지, **v10.3.0에 포함**):

> Download token (`RNMAPBOX_MAPS_DOWNLOAD_TOKEN`) is **no longer required by Mapbox** for accessing their SDKs.

같은 PR에서 config plugin prop에 주석이 달렸습니다.

```ts
/** @deprecated Download token is no longer required by Mapbox. Do not set this. */
RNMapboxMapsDownloadToken?: string;
```

**문서가 고정한 v10.3.1이 바로 이 변경이 들어간 계열입니다.** 자기가 고른 버전의 릴리스 노트를 §7에서 4줄이나 인용해 놓고, 같은 릴리스가 무효화한 요구사항으로 §11을 썼습니다.

**연쇄 피해**

- §11.4 "즉시 실행 항목" 5개 중 3·4·5번(sk. 발급, GitLab Variables 등록, 관련 배포)이 불필요
- §15 항목 7(우선순위 **높음**)의 절반이 소멸
- §8.2(1)의 "Bare는 3곳, Expo는 1곳" 비교표에서 Secret Token 행이 사라짐 → **Expo 선택의 "가장 큰 이유"가 약해짐**

**또한 설계 자체에 모순이 있었습니다.** §11.3은 `sk.`를 `.env.local`에 두고 `app.config.ts`가 읽게 하라고 하면서, §8.3(2)는 `android/` 폴더 커밋을 권장합니다. prebuild 산출물에 토큰이 주입된 상태로 커밋되면 **시크릿이 그대로 Git에 올라갑니다.** 토큰이 불필요해져 결과적으로 해소되지만, 이 조합을 아무도 검토하지 않았다는 신호입니다.

**필요한 조치**: §11을 삭제하고 **Public Token(`pk.`) 관리 3~4줄**로 축소.

## 치명 3 — 문서가 다루는 범위가 앱의 일부입니다

`backend/.../V1__init_schema.sql`의 33개 테이블이 말하는 실제 앱은 이렇습니다.

| 도메인 | 테이블 |
|---|---|
| 인증 | `member`, `social_account` → **소셜 로그인** |
| 푸시 | `fcm_token`, `notification` → **FCM** |
| 실시간 | `chat_message`, `chat_read_status` → **채팅** |
| 파일 | `file_meta`, `post_attachment`, `report_evidence` → **업로드** |
| 커뮤니티 | `post`, `post_comment`, `post_like`, `follow` |
| 부동산 | `apartment`, `apartment_transaction`, `apartment_favorite` |
| 스터디 | `study`, `study_notice`, `study_application`, `study_member`, `schedule` |
| 임장 | `field_session`, `field_participant`, `checklist`, `checklist_item`, `field_record`, `checklist_answer` |
| 리포트 | `report`, `report_evidence`, `report_favorite` |
| AI | `chatbot_conversation`, `chatbot_message`, `apartment_rag_document` |

문서 909줄이 다루는 것: **지도, 캐릭터 스프라이트, 흔들기, 버튼 Lottie.**

전체 문서 단어 검색 결과입니다.

| 검색어 | 등장 |
|---|---|
| 네비게이션 / navigation / 라우팅 | **0회** |
| expo-location / 위치 권한 | **0회** |
| 소셜 / FCM / 푸시 | **0회** |
| 업로드 / secure-store / 채팅 | **0회** |
| edge-to-edge | **0회** |
| 로그인 | 1회 (§12 "인증 토큰 / 로그인 여부") |
| 카카오 | 1회 (§11.3 "토큰을 보내면 안 되는 채널"로) |

**개별 지적**

**(1) 네비게이션 라이브러리 결정이 0줄입니다.** 위 도메인이면 화면이 최소 20개, 탭 + 스택 중첩 + 딥링크입니다. `react-navigation` vs `expo-router`는 **폴더 구조·인증 게이팅·딥링크·상태관리 설계를 모두 규정**하는 최상위 결정인데, §15 "남은 결정 사항" 14개 목록에도 없습니다. `expo-router`를 고르면 §9의 폴더 구조 결정도 다시 써야 합니다.

**(2) 지도 앱인데 `expo-location`이 없습니다.** §8.2(2)의 라이브러리 표에 `expo-sensors`(흔들기)는 있고 `expo-location`은 없습니다. 백엔드에 PostGIS가 깔려 있고 rnmapbox 공식 문서도 LocationPuck에 `expo-location`을 요구합니다. 런타임 위치 권한 플로우(거부/재요청/설정 유도), 정확도·배터리, 포그라운드 서비스 — 임장 앱의 핵심 UX인데 검토가 없습니다.

**(3) §10.1 "직접 작성할 네이티브 파일 0~1개"는 성립하지 않습니다.** `social_account`(카카오/네이버 SDK 연동)와 `fcm_token`(FCM)은 **둘 다 네이티브 설정이 필수**입니다. 증거는 이미 저장소 안에 있습니다 — `.gitignore`에 `google-services.json`이 등재돼 있습니다. 누군가는 FCM을 전제하고 있는데 스택 문서는 모릅니다.

**(4) 실시간 통신이 "중간" 우선순위 한 줄입니다.** §15 항목 12. `chat_message` + `chat_read_status` + 위치 브로드캐스트는 재연결·백그라운드 전환·중복 전송 처리가 필요한 설계 주제입니다. 스프라이트 프레임 크기(§6.1)보다 아래 있을 항목이 아닙니다.

## 높음 4 — §7 하향 비교표에 사실 오류가 있습니다

> "Android 빌드 설정이 두 버전 간 완전히 동일합니다."

npm registry 실측(`react-native@0.84.1` / `0.85.0` / `0.86.0`):

| 항목 | 문서 주장 | 실제 0.84.1 | 실제 0.85.0 |
|---|---|---|---|
| Node 최소 | 22.11.0 (동일) | `>= 20.19.4` | `^20.19.4 \|\| ^22.13.0 \|\| ^24.3.0 \|\| >= 25.0.0` |
| Metro | 미기재 | `^0.83.3` | `^0.84.0` |
| hermes-compiler | 미기재 | `...0.9` | `...0.10` |
| jest preset | 미기재 | 내장 | `@react-native/jest-preset` **peer dep로 분리** |
| React | 19.2.3 (동일) | `^19.2.3` ✅ | `^19.2.3` ✅ |

Node 행은 **양쪽 다 틀렸습니다.** 그리고 "Android 빌드 설정"이라고 제목을 달아놓고 Node·TypeScript·React를 넣었습니다 — 안드로이드 빌드 설정이 아닙니다. Gradle 계열 값(compileSdk/NDK/Kotlin)만 같다면 그건 **AGP가 같다는 뜻이지 RN 버전이 같다는 뜻이 아닙니다.**

이 표가 §7 결론("하향 비용 사실상 0")의 유일한 근거입니다. 근거가 틀렸으니 결론도 재검토 대상입니다.

## 높음 5 — RN 0.86을 한 줄로 기각했는데, 이 프로젝트에 직접 관련됩니다

문서: "0.86 — 동일하게 미검증."

RN 0.86은 **2026년 6월 11일 릴리스**되었고 핵심이 **Android 15+ edge-to-edge 대응**입니다. 공지된 수정 중:

- `measureInWindow`가 edge-to-edge 활성 상태에서 **올바른 좌표 반환**
- `Dimensions` window 값 정확도
- `StatusBar` / `Modal` 상호작용

문서는 `targetSdkVersion 36`을 고정했습니다. **Android 15(API 35) 이상을 타깃하면 edge-to-edge가 강제 적용**되고, 시연 기기는 Android 16입니다.

이 앱의 핵심 화면은 **전체화면 지도 위에 캐릭터를 화면 좌표로 배치**하는 구조입니다. `measureInWindow` 오차는 정확히 이 지점을 때립니다. RN 0.84를 고르면 이 버그를 안고 갑니다.

문서는 이 리스크를 검토조차 하지 않고 "미검증" 한 단어로 넘겼습니다. **`edge-to-edge`가 문서 전체에 0회 등장합니다.**

## 높음 6 — rnmapbox의 0.84 지원을 과장했습니다

> "0.84.1 — **명확히 지원.** 공식 예제 앱이 0.84.1로 검증"

`@rnmapbox/maps@10.3.1` 패키지 매니페스트 실측:

```json
"peerDependencies": { "react-native": ">=0.79" },
"devDependencies":  { "react-native": "0.81.1", "expo": "^54.0.10",
                      "@react-native/babel-preset": "0.81.1" }
```

- **라이브러리 자체의 개발·테스트 하네스는 RN 0.81.1 / Expo SDK 54**입니다
- 0.84.1로 올라간 건 **example 앱뿐**(PR #4202)
- peer 범위는 `>=0.79`로 **0.85·0.86을 명시적으로 배제하지 않습니다**

즉 "0.84는 검증, 0.85는 미검증"이라는 이분법이 성립하지 않습니다. 어느 쪽도 메인 테스트 매트릭스가 아니고, 양쪽 다 peer 범위 안입니다. PR #4200이 고친 것도 **"RN 0.84+ bridgeless"** 크래시 — 0.85·0.86도 포함하는 범위입니다.

## 높음 8 — Mapbox 자체가 검증되지 않은 전제입니다

Mapbox는 §1 "전제 요구사항"에 들어가 있고 근거는 없습니다. 한국 대상 위치 서비스에서 이건 큰 미검토 항목입니다.

- Mapbox 기본 스타일은 OSM 기반 — **한국 POI 밀도와 한글 라벨 품질**이 네이버/카카오맵과 차이가 큽니다
- 앱 도메인이 **아파트·실거래가·임장**입니다. 단지명·동호수·주변시설 라벨이 부정확하면 제품이 성립하지 않습니다
- 네이버지도 SDK / 카카오맵 SDK 비교가 0줄

**전제라면 "누가 준 제약인지" 명시**하고, 선택이라면 근거가 있어야 합니다. 1일차 스파이크에 **"S23에서 대상 아파트 단지를 Mapbox로 띄워 한글 라벨·POI 확인"** 을 추가하십시오. 이게 §6의 스프라이트 프레임 측정보다 먼저입니다.

## 중간 9~14

**9. 스프라이트 fps 권장이 애니메이션 내용과 맞지 않습니다.**
§6.1은 "8~12fps로 충분"이라 하는데, 37프레임 ÷ 10fps = **3.7초/사이클**입니다. 걷기 모션이면 슬로우모션입니다. 37프레임은 24~30fps 기준 1.2~1.5초짜리 동작으로 만들어졌을 가능성이 높습니다. **프레임 수만 보고 무슨 동작인지 묻지 않았습니다.** 아트 발주 전에 반드시 확인해야 하는 항목인데 §15 항목 8에도 "재생 fps"만 있고 "동작 길이"가 없습니다.

**10. 메모리 계산과 아틀라스 분할 권장이 서로 어긋납니다.**
"185프레임 총량 기준 512×512 = 194MB → 불가" 판정을 내린 직후, 바로 아래에서 **"방향당 1장으로 분할"** 을 권장합니다. 분할하면 동시 상주는 전체 185프레임이 아니라 **표시 중인 방향의 아틀라스뿐**입니다. 전제(전량 상주)와 권장(분할 로딩)이 모순이라 상한값 자체를 신뢰할 수 없습니다.

**11. Flutter 반박 근거의 시효가 지났습니다.**
flutter#167547은 실재하고 여전히 open(P2)이지만, 보고자 테스트 환경이 **Flutter 3.24.5 / 3.27, 2025년 4월**입니다. 2026년 HCPP 도입 이후를 다루지 않습니다. 문서는 §2.1 "공정한 반론"에서 이걸 스스로 인정하고도 결론을 바꾸지 않습니다. **RN 결정 자체는 옳지만 근거로 이 인용을 앞세우면 방어가 안 됩니다.** 실제 결정 근거는 "팀의 React 경험 + 2~3주"이고, 그건 §2.2 "부차적 사유"에 밀려 있습니다. 논증 순서가 실제 가중치와 반대입니다.

**12. Dev Menu shake 비활성화 1순위에 근거가 없습니다.**
§8.3(1)은 "`DevSettings` API로 shake 트리거 비활성화 가능 여부 확인"을 1순위로 둡니다. RN의 JS `DevSettings` 모듈에 shake 토글은 없습니다(유사 속성은 iOS `RCTDevSettings` 쪽). 다만 **`expo-dev-client`는 자체 dev menu에 모션 제스처 설정을 제공**하므로, Expo를 쓰면 해결될 가능성이 높습니다 — **근거가 다릅니다.** "RN JS API"가 아니라 "expo-dev-menu 설정"으로 고쳐 쓰고, 스파이크에서 확인하십시오.

**13. Hermes V1 언급이 없습니다.**
RN 0.84의 헤드라인 변경은 **Hermes V1 기본 채택**입니다. 문서에서 "Hermes"는 §5의 "무관" 표에 1회 등장할 뿐입니다. 엔진이 바뀐 버전을 고정하면서 엔진 얘기가 없습니다. Expo SDK 56도 Hermes V1이 기본입니다.

**14. 릴리스 빌드 경로가 없습니다.**
시연 APK를 어떻게 만들어 S23에 넣는지가 없습니다. keystore(`.gitignore`에 이미 `*.jks`, `*.keystore`), 서명, R8/ProGuard, EAS vs 로컬 release 빌드. §15 착수 순서는 개발 시작까지만 다루고 산출물에서 끝납니다. 2~3주 프로젝트에서 릴리스 빌드를 마지막 날 처음 돌리면 사고가 납니다.

## 문서 형식 15~17

**15. ADR 형식이 아닙니다.** 결정 문서에 있어야 할 것 — 소유자, 결정일, **재검토 트리거**, 대안별 폐기 사유, 되돌리는 비용 — 이 없습니다. §12.3의 "나중에 바꾸는 비용" 표가 유일하게 이 성격을 갖는데, 그 사고를 다른 결정에는 적용하지 않았습니다.

**16. "초판 정정"이 본문에 섞여 있습니다.** §4의 ⚠️ 블록은 훌륭한 자기수정이지만 **본문이 아니라 변경 이력**에 있어야 합니다. 지금은 읽는 사람이 "무엇이 결정인가"와 "무엇이 철회된 과거 주장인가"를 매번 분리해야 합니다.

**17. 튜토리얼과 결정이 섞여 46KB가 됐습니다.** §3.3(안드로이드는 프레임워크가 아니다), §5(Java/Kotlin 성능·빌드 검증), §10.3(TurboModule이란), §13.1~13.2(Android Studio가 JS를 못 하는 이유)는 **결정이 아니라 설명**입니다. 특히 §4+§5는 **파일 2개의 문법 선호**에 90줄을 씁니다. 그 사이에 네비게이션 결정은 0줄입니다. 지면 배분이 중요도와 반대입니다.

설명은 `docs/ANDROID_BACKGROUND.md`로 분리하고, 결정 문서는 **결정과 근거만** 남기십시오. 팀이 실제로 읽습니다.

## 반대로, 잘된 부분

깎기만 하면 공정하지 않습니다.

- **§4의 자기수정.** "초판에서 이렇게 썼는데 사실이 아니다"를 명시하고 판단 근거에서 제외한 건 드문 태도입니다
- **§2.1의 반론 병기.** HCPP가 자기 논증을 약화시킨다는 걸 숨기지 않았습니다
- **§6.1의 Rive 기각 근거.** "프레임 단위 래스터 재생 프리미티브가 없다"는 정확한 기술적 판단입니다
- **§12.3 주의 사항.** "프레임 인덱스를 zustand에 넣지 마라, Reanimated shared value로" — 실제로 사람들이 틀리는 지점을 정확히 짚었습니다
- **§12의 "바꾸는 비용" 축.** 이 사고를 나머지 결정 전체에 확장하면 문서가 훨씬 짧고 강해집니다

**RN + Expo + TypeScript라는 큰 방향 자체는 타당합니다.** 문제는 방향이 아니라 **그 아래 채워진 구체값이 검증되지 않았고, 앱의 나머지 85%가 비어 있다**는 점입니다.
